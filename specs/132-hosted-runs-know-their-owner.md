# Spec 132: Hosted runs know their owner

Split from spec 104 on 2026-10-12 (spec 104, "Amendment (2026-10-12):
split into hosted mode, run ownership, store password and the request
transaction", decision 1). This is part B. Spec 104 is part A, hosted mode
and the bearer token; spec 133 is part C, the store password; spec 134 is
part D, the request transaction and the start checks. The order is A, then
B, then D, and D lifts the gate that keeps the hosted API from serving.
This text is spec 104's Scope item 7, its Behavior sections "Runs" and the
expiry half of "The event stream", and the criteria that went with them,
restated with one gap closed (Where spec 104's text was wrong, below).

## Problem

The run registry is one in-memory dict per process
(`services/api/src/harrier_api/runs.py`, `RunManager`). `GET /runs` lists
every run, and `GET /runs/{run_id}`, `POST /runs/{run_id}/cancel` and
`GET /runs/{run_id}/events` answer for any id that exists
(`services/api/src/harrier_api/app.py`, `list_runs`, `get_run`,
`cancel_run`, `stream_run_events`). Locally there is one operator, so
that is right.

Hosted, spec 104 makes every one of those routes require a verified bearer
token, and nothing more. Any signed-in owner can then list another owner's
runs, read their events and cancel them. And a run's subprocess inherits
the server's environment (spec 035, Problem), so a run started from a
hosted request would spend the operator's Apify and LLM keys on a tenant's
behalf and open the store as the API's login role. Spec 106 gives a run its
owner's credentials and database identity. Until it lands, no run may start
hosted. ADR-013 decision 4 says a run started from a request records its
owner, and a run with no owner is refused before it starts.

The event stream has a second problem. A token proves who called at the
moment it was checked. A stream opened with a token that expires in a
minute would keep sending events for as long as the run lasts, so the
stream outlives the authority that opened it.

## Scope

1. **`Run` gains `owner: str`.** Empty locally. Hosted, the `sub` of the
   request that started the run. It is written to the run journal with the
   other fields, and a journal entry written before this spec reads back
   with an empty owner.
2. **Run routes are limited to the run's owner, hosted.** Listing, reading,
   cancelling and streaming (Behavior).
3. **Starting a run hosted is refused** with a new exception,
   `RunsNotHosted`, answered 501, until spec 106. The refusal is in the two
   places every run route reaches before a file or a process exists
   (Behavior).
4. **The event stream ends when the token that opened it expires.**
5. **The contract** declares the 501 on every route that can start a run.
   `packages/contract/openapi.json` and
   `packages/contract/src/schema.d.ts` are regenerated by `just contract`.
   A guarded path, approved under this spec.

Hosted mode is spec 104's: `HARRIER_AUTH=supabase`, read from the process
environment. The request's `sub` and `exp` are the verified claims spec
104's middleware attaches to the request. This spec adds no variable, no
dependency, no table and no migration. Every file it changes sits under
`services/api/src/`, `services/api/tests/` and `packages/contract/`, which
`config/data-classification.json` already classifies as public. The run
journal is under `data/`, which it classifies as never-in-git.

## Behavior

### The owner

`RunManager.start` takes the owner from its caller. Every route that starts
a run passes the request's `sub` hosted and the empty string locally. The
owner is part of the run's journal entry. `_load_journal` reads an entry
without the field as owner empty, so a journal written before this spec
still loads.

### Run routes, hosted

- `GET /runs` lists only the runs whose owner is the request's `sub`.
- `GET /runs/{run_id}`, `POST /runs/{run_id}/cancel` and
  `GET /runs/{run_id}/events` answer 404 `run not found` for a run whose
  owner is not the request's `sub`. That is the answer for an id that does
  not exist, so a response does not tell one owner that another owner's
  run id exists.
- A run with an empty owner is no one's hosted: it is listed to no one and
  answered 404 to everyone.

Locally the owner is empty for every run, every run is listed, and every
route answers as it does today.

### Starting a run, hosted

`RunManager.start` raises `RunsNotHosted` hosted, before it writes a
journal entry, registers a run or spawns a process. `write_run_input`
(`services/api/src/harrier_api/runs.py`) raises it too, before it creates
the run inputs directory or a file. Three routes write their input before
they call `start` (Where spec 104's text was wrong, below), so a refusal in
`start` alone would leave a file behind.

An exception handler answers `RunsNotHosted` with 501 and `ErrorOut`
detail `runs are not available on the hosted API until spec 106`. Both
refusals sit in functions every run route calls, so a new run route
cannot bypass them.

A run with an empty owner is refused by `start` hosted with the same
exception. This is ADR-013 decision 4's "a run with no owner is refused
before it starts". Until spec 106 every hosted start is refused anyway;
the owner check is what stays when spec 106 lifts the 501.

The 501 is declared, with `ErrorOut`, by the same constant that declares
the run conflict: `RUN_CONFLICT_RESPONSES`
(`services/api/src/harrier_api/runmodels.py`) gains it. Every route that
calls `start` declares that constant today, and the contract criterion
below walks the routes to hold the two together. The local API never
sends the 501; its document is the
same document, so `just contract` needs no mode.

### The event stream

`GET /runs/{run_id}/events` hosted reads the `exp` of the verified claims
of the request that opened it. When `exp` passes, the stream sends a final
SSE comment line, `: token expired`, and ends. Locally there is no token
and the stream ends as it does today, when the run is terminal.

The browser reconnects with a fresh token and `Last-Event-ID`, which the
route already honours (`stream_run_events`), so no event is lost. Spec 104
keeps the rule that the token is read only from the `Authorization`
header.

### Where spec 104's text was wrong

Spec 104 said `RunManager.start` refuses "before it writes an input file
or spawns anything". `start` writes no input file. Three routes call
`write_run_input` before they call `start`:
`services/api/src/harrier_api/app.py` (`tailor`'s free text),
`services/api/src/harrier_api/ops_routes.py` (discovery's uploads) and
`services/api/src/harrier_api/outreach_routes.py` (the draft's payload).
A refusal in `start` alone would come after those files exist. This spec
therefore refuses in `write_run_input` as well, and its criterion checks
the run inputs directory, not only `start`.

## Failure modes

- **Another owner's run id.** 404 `run not found`, the same body as an
  unknown id.
- **Cancelling another owner's run.** 404; the run is not cancelled.
- **Starting a run hosted.** 501 with the spec 106 text. No journal
  entry, no file under the run inputs directory, no process.
- **A route that writes its input before `start`.** `write_run_input`
  refuses first: 501, no file.
- **A run with an empty owner, hosted.** Not listed, 404 on every run
  route, refused by `start`.
- **A journal entry from before this spec.** Read with an empty owner.
  Locally nothing changes; hosted no one sees it.
- **The token expires mid-stream.** The stream ends with the final comment
  line. A reconnect with an expired token is spec 104's 401 `expired`.
- **The token expires while no event is pending.** The stream still ends
  at `exp`, not at the next event.

## Honest limitations

- Until spec 106 no hosted run exists, because every start is refused. The
  owner filter guards runs that reach the registry another way: a journal
  in the image, or a test. It is built now so that spec 106 lifts only the
  501 and cannot forget the filter.
- The registry is still one dict per process (spec 041). Two API machines
  hold two registries, and a run on one is not found on the other. Spec
  107 leaves the run manager's own files to spec 106
  (`specs/107-artifacts-and-run-state-in-storage.md`, its table of local
  files), so hosted runs, and where their state lives, are spec 106's.
- The stream ends at `exp` as this process's clock reads it. Clock
  synchronization on the Fly machine is assumed, as spec 104 assumes it.
- A cancelled stream does not cancel the run. That is spec 006's behavior
  and is unchanged.

## Migration

None. The journal gains a field that an old entry lacks and reads as
empty. No variable, file or route changes for the local product.

## Options weighed

- **Refuse only in `start`.** What spec 104 said. It leaves an input file
  behind on three routes. Not chosen.
- **Answer 404 on every run route hosted until spec 106.** Spec 104's Open
  decision 5 alternative. It hides the routes rather than saying why they
  refuse, and leaves the owner filter for spec 106 to remember. Not chosen
  (spec 104, Open decision 5).
- **Declare the 501 by the route class.** `DatabaseRoute` can see a
  dependency on `Conn`; it cannot see that an endpoint calls `start`. The
  run conflict constant is already on exactly the routes that can start a
  run. Not chosen.

## Open decisions for Akin

1. **The comment line's text.** Recommended: `: token expired`. It names
   why the stream ended, carries no claim value, and the browser ignores
   comment lines. Alternative: an SSE event with its own type, which the
   browser would have to handle and the contract would have to declare.

## Amendment (2026-10-12): what building it settled

Building this spec showed one place where the text was wrong and settled
the points below, so the code and the spec agree.

### Where the text was wrong

- **Six routes write their input before `start`, not three.** "Starting a
  run, hosted" and "Where spec 104's text was wrong" name one route per
  file. In `services/api/src/harrier_api/app.py`, `_apply_params` writes
  the free text for all four apply routes (`tailorResume`,
  `draftCoverLetter`, `draftAnswers`, `evaluateOffer`), so six routes in
  the three files named write a file before `start`. The refusal in
  `write_run_input` covers all six. The 501 test has one case per route
  and marks the six, and for each of the others it checks that `start`
  was reached with the caller as owner
  (`services/api/tests/test_run_owner.py::test_a_kind_not_offered_hosted_answers_501_naming_its_spec`).
- **One file outside the Scope's paths changes.** Spec 104's "Runs and
  stream" criteria marked three of this spec's tests as planned. The
  citation check fails a planned test that exists, so
  `specs/104-the-hosted-api-authenticates-every-request.md` now cites them
  as built. No other text of spec 104 changes. Inside the Scope's paths,
  `own_causes` in `services/api/tests/conftest.py` sets the 501's cause
  beside the 409's, as one declared by mechanism, so a route's own causes
  are still checked without it.
- **The web app changes too.** The Scope said every changed file sits
  under `services/api/` and `packages/contract/`. The contract review of
  PR #300 found three run starts on the Operations page that read only the
  run and took any other answer for the local token's refusal: the feed
  check (`apps/web/src/pages/operations/FeedsSection.tsx`), the decision
  history backfill (`HistorySection.tsx`) and the feature export
  (`ScoringSection.tsx`), in the same directory. Hosted, the operator
  would have read "the local API token was not accepted" instead of the
  501's words; the same gap already hid their 409. Each now reads the
  refusal body through `refusalMessage`, as every other run start does,
  and `apps/web/src/shared/api/refusal.ts` names the 501 among the
  refusals it reads. The files are public: none matches a never-in-git
  pattern in `config/data-classification.json`, and public is the
  complement of those.

### What the build settled

- **Open decision 1 takes the recommended answer.** The stream's last
  line at expiry is the SSE comment `: token expired` (`TOKEN_EXPIRED_LINE`
  in `services/api/src/harrier_api/runmodels.py`).
- **Where "hosted" is read.** `runs_hosted` in
  `services/api/src/harrier_api/runs.py` reads `HARRIER_AUTH=supabase`
  from the process environment each time it is asked (`hosted_mode` in
  `services/api/src/harrier_api/hostedauth.py`). `start`,
  `write_run_input` and the owner view all ask it, so the three agree.
  `write_run_input` has no request, which is why the process environment,
  and not the assembled app, is the source. So that the app and the run
  manager cannot disagree, `create_hosted_app` refuses with
  `HostedConfigError` unless the variable is set
  (`services/api/tests/test_run_owner.py::test_the_hosted_app_needs_hosted_mode`).
  `create_app` builds the hosted app only when it is set, and the local
  app only when it is not. Spec 104's tests in
  `services/api/tests/test_hosted_auth.py` therefore set it before they
  build the hosted app, and unset it before they build the local one
  (test-integrity review of PR #300).
- **The owner is passed in one place.** `Manager`, the dependency every
  run route takes, is now `OwnedRuns` in
  `services/api/src/harrier_api/runmodels.py`: the run manager as the
  request's owner sees it. Its `start` passes the request's `sub`, and its
  `list_runs`, `get`, `cancel` and `stream` apply the owner filter. No
  route passes an owner itself, so a new route cannot pass the wrong one.
  `stream` refuses a run its owner does not see with `KeyError`, as an
  unknown id, rather than relying on the route to ask `get` first
  (test-integrity review of PR #300,
  `services/api/tests/test_run_owner.py::test_another_owners_run_is_not_found`).
- **A hosted request without verified claims.** The middleware lets none
  through; this is the second line. Such a view has the empty owner, so it
  sees no run, and it takes `exp` as passed, so a stream it opened ends at
  once
  (`services/api/tests/test_run_owner.py::test_a_run_without_an_owner_is_no_ones`).
- **The backups list reads runs too.** `GET /settings/backups` marks each
  archive with the latest verification run the registry holds
  (`_verification` in `services/api/src/harrier_api/settings_routes.py`).
  It reads the runs through the same view, so hosted it marks an archive
  only from the caller's own verification runs. The Behavior section named
  the run routes only; this route reads runs, so the same rule holds.
- **No leeway on the stream.** The verifier accepts a token up to 30
  seconds past its `exp` (spec 104, The token). A stream opened with such
  a token ends at once, before any event, because `exp` has passed.
- **The contract's words.** The 501 is declared with `ErrorOut` and the
  description `hosted only: runs are not available on the hosted API
  until spec 106`.

### Acceptance criteria (amendment of 2026-10-12)

- [ ] Hosted, the backups list marks an archive only from the caller's
      verification runs
      (`services/api/tests/test_run_owner.py::test_a_backup_verification_is_its_owners`).
- [ ] A refusal to start a run, the hosted 501 among them, reaches the
      operator in the API's words on the feed check, the decision history
      backfill and the feature export
      (`OperationsPage.test.tsx::a hosted refusal to start a run is shown in the API's words`).

### Honest limitations (as built)

- The hosted half of "a run records its owner" is proven up to `start`,
  which refuses. No hosted run exists until spec 106, so no test reads a
  hosted run's journal entry with its owner.
- The stream test runs on the wall clock: its token expires at least
  three seconds after it is minted, and the stream must end within ten.
  A machine that stalls longer than that fails it.

## Note (2026-10-13): spec 106 lifts the 501

Spec 106 is built. Hosted, a run starts when its kind is one spec 106's
table offers and the request carries an owner; a run with an empty owner
is still refused before it starts, now with `a run on the hosted API needs
an owner`, and a kind the table refuses answers 501 naming its spec. The
two citations of the test that proved every hosted start refused are
re-cited to the test that replaced it, which covers the refused kinds with
one case per route
(`services/api/tests/test_run_owner.py::test_a_kind_not_offered_hosted_answers_501_naming_its_spec`).
A hosted run's journal entry no longer exists: spec 106 records hosted
runs in `run_records`. Nothing else in this spec changes.
