# Spec 116: Tenant credentials are stored encrypted

Split from spec 106 on 2026-10-10. This text was spec 106's "Part A, the
credential store", moved here with its sections unchanged except for
numbering. It lands first. Spec 106 keeps "runs as their owner" (its
former Part B), reads what this spec stores through one function, and
depends on this spec. This spec can be built and merged with no run using
it.

## Problem

Credentials live in one `.env`, and a run's subprocess inherits the server's
whole environment (spec 035). Hosted, each owner brings their own keys: Akin
chose bring-your-own LLM keys (spec 102, open decision 3), and ADR-013
decision 8 stores credentials per owner and gives each run only its
owner's.

The post-merge review of PRs #194 and #207 (2026-10-10, architecture 10)
found that the credential key has no home. Credentials are encrypted at
rest, and a spec must name where the encryption key lives (Supabase Vault
or a KMS, the stub said) and decrypt an owner's credentials only at run
start. Spec 106's stub owned that finding; this spec now does, and spec
106 owns the decryption at run start.

Credentials are read from the environment by name today: `OPENAI_API_KEY`
and `ANTHROPIC_API_KEY` (`services/api/src/harrier/llm/config.py:131-153`),
`APIFY_TOKEN` (`sources/apify_linkedin.py:42`, `sources/apify_academic.py:51`,
`outreach/discovery.py:56`), `HUNTER_API_KEY` (`outreach/hunter.py:23`),
`TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID` (`notify.py:32-33`). Spec 106
gives a run its owner's values under those names; this spec stores them.

Line numbers are from `main` at `44ac0d7` (2026-10-10), except the
`schema.py` ones, refreshed to `main` at `524dd8a` on 2026-10-11.

## Behavior

The trust model this store sits in is spec 106's ("The trust model"): the
API process holds the key and can reach every owner's decrypted
credentials; the database holds ciphertext only.

### Credential kinds

| Kind | Fields (all text) | Secret fields | Set by | Reaches a run as |
|---|---|---|---|---|
| `ai` | `provider` (`openai-api` or `anthropic-api`), `key`, `model` (optional) | `key` | `PUT /credentials/ai` | `AI_PROVIDER`, `OPENAI_API_KEY` or `ANTHROPIC_API_KEY`, `AI_MODEL` when set |
| `apify` | `token` | `token` | `PUT /credentials/apify` | `APIFY_TOKEN` |
| `hunter` | `key` | `key` | `PUT /credentials/hunter` | `HUNTER_API_KEY` |
| `telegram` | `bot_token`, `chat_id` | `bot_token`, `chat_id` | spec 109's route only | `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` |

The Telegram chat id is secret everywhere (decision D7, 2026-10-11): it
is stored encrypted alongside `bot_token`, in the same ciphertext, and
spec 106 scrubs it from run events and summaries as it scrubs every
secret field.

One AI credential per owner: its provider decides which key variable is
set, so a run never holds two AI keys. `gmail` is not a kind until the
Gmail follow-on of spec 109 adds it; the `CHECK` below refuses it.

Each field is stripped of surrounding whitespace. A field is refused when
it is empty (except `model`), longer than 4096 bytes in UTF-8, or holds a
control character, NUL or newline included, because the value becomes an
environment variable. 4096 is a chosen bound, not a measured one.

### Storage

The new migration, Postgres only:

```sql
CREATE TABLE credentials (
    owner_id uuid NOT NULL DEFAULT auth.uid() REFERENCES auth.users (id),
    kind text NOT NULL CHECK (kind IN ('ai', 'apify', 'hunter', 'telegram')),
    key_id text NOT NULL,
    nonce bytea NOT NULL,
    ciphertext bytea NOT NULL,
    updated_at text NOT NULL DEFAULT <spec 103's timestamp expression>,
    PRIMARY KEY (owner_id, kind)
);
```

It gets spec 105's shape whole: row security enabled and forced, the one
`owner_only` policy `FOR ALL TO harrier_tenant`, `REVOKE ALL` from
`PUBLIC`, `anon`, `authenticated` and `service_role`, and `GRANT SELECT,
INSERT, UPDATE, DELETE` to `harrier_tenant`. The primary key leads with
`owner_id`, which is the owner index the catalog test asks for.
`services/api/tests/test_owner_policy.py::test_every_table_is_owned_or_declared`
holds it to that shape once `credentials` is in `OWNED_TABLES` and the
grants list.

SQLite gets no table. Locally credentials stay in `.env`, and a local
`credentials` table would be a second place for local secrets, inside the
file `just backup` copies. `HOSTED_ONLY_TABLES = {"credentials": "per-owner
encrypted credentials (spec 116); local credentials live in .env"}`.

Writes are update, then insert when no row changed, then the update once
more on a unique violation: spec 112's upsert shape, naming no tenant.

### Encryption and the key's location

- **Algorithm.** AES-256-GCM from `cryptography`'s `AESGCM`, which the
  `hosted` dependency group already brings through `pyjwt[crypto]` (spec
  104, Scope 11). A fresh random 96-bit nonce per write, the length NIST
  recommends per the `cryptography` documentation.
- **What is encrypted.** The kind's fields as one JSON object.
- **Associated data.** `harrier-credential:v1:<owner_id>:<kind>`. A
  ciphertext copied to another owner's row or another kind fails to
  decrypt, because GCM's tag covers the associated data.
- **The key lives on Fly, the ciphertext on Supabase.** The key is a Fly
  secret on the API app, `HARRIER_CREDENTIALS_KEY`, formatted
  `<key id>:<base64 of 32 bytes>`. Fly stores secrets in an encrypted
  vault and injects them into the machine's environment at boot (Fly
  secrets documentation). The database row records the key id. Reading the
  database, its backups, or the Supabase dashboard yields ciphertext and
  never the key; reading the key alone yields nothing to decrypt. An
  attacker needs both vendors.
- **Who decrypts.** Only `RunManager.start` in the API process, at run
  start, for the run's owner (spec 106). No route decrypts. `GET
  /credentials` reads `kind` and `updated_at` and never selects
  `ciphertext`.
- **The child never holds the key.** It is not on the allowlist.

The API refuses to start hosted when `HARRIER_CREDENTIALS_KEY` is absent,
not of that form, or does not decode to 32 bytes, naming the variable and
never its value: `error: HARRIER_CREDENTIALS_KEY must be <key id>:<base64
of 32 bytes>`, exit 1. Locally it is ignored.

### Routes

Hosted, under spec 104's bearer token and request transaction:

| Route | Body | Answer |
|---|---|---|
| `GET /credentials` | none | 200 `CredentialsOut`: one item per kind in the table above, `{kind, set, updated_at}`; `updated_at` null when unset |
| `PUT /credentials/{kind}` | `AiCredentialIn`, `ApifyCredentialIn` or `HunterCredentialIn` by kind | 200 `CredentialStatusOut` `{kind, set: true, updated_at}` |
| `DELETE /credentials/{kind}` | none | 200 `CredentialStatusOut` with `set: false`; also when nothing was stored |

`PUT /credentials/telegram` answers 404: spec 109's route writes that
kind, after it has checked the bot. An unknown kind answers 404.

No answer, error detail or log record carries a submitted value. FastAPI's
default 422 body echoes the submitted input; on these routes the 422 body
names the field and the rule only (`detail: [{field, problem}]`), and the
request body is never logged.

Locally every credentials route answers 404 `credentials are read from
.env on the local API`. The routes are in the one contract, as spec 104
requires of hosted-only behavior.

### ADR-013 decision 8, amended

Decision 8 gains: "**Amended (spec 116).** The key that encrypts tenant
credentials is a Fly secret on the API app; the ciphertext is in Supabase.
Only the API process decrypts, at run start (spec 106)."

## Failure modes

- **No key, or a malformed key, hosted.** Start refused naming
  `HARRIER_CREDENTIALS_KEY`, exit 1.
- **The key is replaced, or a row's key id is unknown.** That owner's runs
  needing the credential are refused with the 409 `cannot be read; set it
  again`. Nothing is guessed and nothing else fails.
- **A ciphertext moved to another owner's row or another kind.** Does not
  decrypt (`InvalidTag`); the same 409.
- **A submitted value that is empty, too long, or holds a control
  character.** 422 naming the field and the rule, never the value. Nothing
  is written.
- **`PUT /credentials/telegram` or `gmail`.** 404. Telegram is spec 109's
  route; Gmail is not a kind.
- **Another owner's credential.** Unreachable by policy: reads see zero
  rows, writes store the session's owner only (spec 105).
- **A credentials route on the local API.** 404 with the local text.
- **The migration on a store without spec 105's auth objects.** Refused as
  migration 10 is; the store stays at its previous version.
- **A credentials table on SQLite, or a declared table missing on
  Postgres.** The parity test fails naming it.

## Honest limitations

- **The API process is the single point that holds everything.** Its
  compromise exposes every owner's credentials. Splitting the key from the
  data protects only against a database-side breach.
- **Key rotation is not built.** One key at a time. Replacing it makes
  every stored credential unreadable, and owners set them again. A keyring
  with re-encryption is a later spec.
- **Losing the key loses every credential.** Owners set them again; no
  data other than credentials depends on it.
- **No credential is checked against its vendor when set.** A wrong key is
  found by the first run that uses it. Spec 109 checks Telegram's.
- **One AI credential per owner.** An owner with both providers' keys
  chooses one.
- **The migration's version is not fixed here.** It is the next free
  version when implemented.
- The line numbers cited here are refreshed by the change that implements
  this spec, not before (decision D9, 2026-10-11).

## Migration

None for the local product. SQLite records the new version and changes
nothing; no local variable changes meaning.

A hosted store reaches the new version through `harrier store migrate`.
The new table starts empty. A hosted deploy needs `HARRIER_CREDENTIALS_KEY`
as a Fly secret before this spec's API starts (spec 110).

## Options weighed

- **Supabase Vault for the key.** Vault encrypts with libsodium
  authenticated encryption and never stores the key beside the data, and a
  dump holds only ciphertext (Vault guide). But secrets are read through
  `vault.decrypted_secrets`, which decrypts for any role that can select
  from it, and Vault is one store for the whole project, not policed per
  owner. Harrier would need a `SECURITY DEFINER` function returning the
  caller's secrets, which spec 105's catalog test refuses in `public`, and
  anyone with the `postgres` role in Supabase's SQL editor could read every
  owner's credentials. Not chosen: the key and the data would sit with one
  vendor.
- **An external KMS (AWS KMS, Google Cloud KMS).** Envelope encryption with
  a key that never leaves the KMS is the strongest of the three. It adds a
  cloud vendor, which the Local-first invariant's closed list (amended by
  spec 102) does not name, and a network call per run start. Not chosen
  now; a later spec could move the key there without changing the table.

## Open decisions for Akin

1. **Split.** Applied in this text: the credential store is its own spec,
   landing first, and spec 106 depends on it. The repository's rule is to
   split the spec, not the branch, and the store is behavior a reviewer
   can check on its own. Alternative: one spec, two pull requests in
   order, as spec 112 was delivered.
2. **Where the key lives.** Recommended: a Fly secret on the API app, data
   on Supabase, so a breach of either alone yields nothing. Alternatives:
   Supabase Vault behind a definer function (one vendor holds both, and
   spec 105's catalog test changes); an external KMS (a new cloud vendor,
   an invariant change).
3. **The hosted-only table.** Recommended: `credentials` exists on Postgres
   only, declared in `HOSTED_ONLY_TABLES`. Alternative: the same table in
   both dialects, unused locally, which needs no new declaration and puts
   an empty secrets table in the local tracker file.
