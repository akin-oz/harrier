# Spec 103: A Postgres store opens at the tracker's current schema

## Problem

The tracker exists only as SQLite. `services/api/src/harrier/tracker/schema.py`
holds nine migrations written in SQLite's dialect, `harrier.db.connect`
opens only `sqlite3`, and the migration runner (spec 090) takes SQLite's
write lock with `BEGIN IMMEDIATE`. ADR-013 decision 1 makes the hosted
store Supabase Postgres, and decision 5 requires one schema definition
for both dialects and harrier's own runner for both. Nothing can be built
on a hosted store until that store exists with the same tables and the
same refusals as the local one.

The SQLite DDL does not run on Postgres as written. Six constructs differ:

- `datetime('now')` and `strftime('%Y-%m-%dT%H:%M:%SZ', 'now')` defaults
  (`schema.py:127`, `:280` and four more tables).
- `GLOB` in the slug CHECK (`schema.py:321-322`) and the deadline CHECK
  (`schema.py:386`). ADR-012 point 5 already names a regular-expression
  CHECK as the Postgres form.
- `RAISE(ABORT, ...)` triggers: two make `job_events` append-only
  (`schema.py:300-306`), two stand in for the foreign key SQLite refuses on
  an added column (`schema.py:343-354`), two protect `tracks`
  (`schema.py:359-367`).
- `INTEGER PRIMARY KEY` as a rowid alias. Migration 8 inserts track `id = 1`
  explicitly (`schema.py:333-334`); a Postgres identity column does not
  advance its sequence for an explicit id, so the next default insert would
  collide with it.
- Migrations 5 and 6 rebuild or drop for SQLite reasons
  (`schema.py:227`, `:244-259`). Postgres never had the old shapes.
- `BEGIN IMMEDIATE` in the runner (`db.py:322`). Postgres needs its own
  way to make two first opens apply each migration once.

The rest of the domain (the write path, readers, upserts, `COLLATE NOCASE`,
`lastrowid`, `sqlite3.IntegrityError`) is out of this spec. It is SQL in
nine modules (`tracker/store.py`, `tracks.py`, `userconfig/store.py`,
`profile/store.py`, `runoutcome.py`, `mail/watch.py`, `logredact.py`,
`apply/profile.py`, `resume/content.py`) and the `sqlite3.Connection`
annotation in about thirty more. That is spec 112. Splitting here keeps
each change reviewable against its spec, as `change-boundary` asks.

## Scope

1. **The store URL.** `HARRIER_DATABASE_URL`, read from the environment.
   Unset or empty: the local SQLite store, exactly as today. A
   `postgresql://` URL: the Postgres store. Any other scheme is refused.
2. **The Postgres driver** is psycopg 3, in a new optional dependency
   group `postgres` in `services/api/pyproject.toml`, like the `pdf` group.
   A local install without it is unchanged.
3. **Migrations declare both dialects together.** Each entry in
   `MIGRATIONS` carries its SQLite statements and its Postgres statements.
   Migrations 1 to 9 keep their SQLite statements unchanged and carry no
   Postgres statements. A Postgres baseline, recorded as version 9, creates
   the schema that SQLite reaches after migration 9. Every migration after
   9 must carry both lists; a test fails if one is empty.
4. **The Postgres baseline** maps each construct listed under Problem:
   - `id` columns are `bigint generated by default as identity primary
     key`. After seeding track 1, the baseline advances the `tracks`
     sequence past it.
   - Timestamp defaults produce the same text formats SQLite produces:
     `YYYY-MM-DD HH:MM:SS` in UTC where SQLite uses `datetime('now')`, and
     `YYYY-MM-DDTHH:MM:SSZ` for `job_events.at`. Columns stay `text`, so no
     value read through the API changes shape.
   - The slug CHECK is `slug ~ '^[a-z][a-z0-9-]{0,31}$'`. The deadline
     CHECK is `deadline = '' OR deadline ~ '^[0-9]{4}-[0-9]{2}-[0-9]{2}$'`.
   - `jobs.track_id` is a real foreign key to `tracks(id)`. The two
     SQLite triggers that stand in for it have no Postgres counterpart.
   - `job_events` append-only, tracks never deleted, and a track id never
     changing are PL/pgSQL trigger functions raising the same message
     texts the SQLite triggers raise.
   - Partial unique indexes on `jobs.url` and `jobs.external_key`, the
     CHECKs on `status`, `tracks.kind`, `job_events.kind`, `actor`,
     `backfilled` and the outcome/company rule are written as in SQLite.
5. **The runner speaks both.** `_apply_schema` runs Postgres migrations
   each inside one transaction (Postgres DDL is transactional, so spec
   090's whole-or-nothing rule holds), after taking a transaction-scoped
   advisory lock and re-reading the version under it, the Postgres
   counterpart of `BEGIN IMMEDIATE`.
6. **Opening a Postgres store never migrates it.** ADR-013 decision 3
   gives requests a role that cannot run DDL. Opening checks the store's
   version and refuses if it is behind the code. Migration is one explicit
   command: `harrier store migrate`, which applies pending migrations to
   the store `HARRIER_DATABASE_URL` names and prints the version before
   and after. `harrier store status` prints the dialect and version.
7. **Nothing else uses the Postgres store yet.** Until spec 112, every API
   start and every CLI command except `harrier store` refuses to run while
   `HARRIER_DATABASE_URL` names a Postgres store, so no process silently
   uses SQLite while the operator believes it uses Postgres.
8. **The parity test** opens a fresh SQLite store and a fresh Postgres
   store and compares them (see Behavior).
9. **CI runs the Postgres tests.** `.github/workflows/ci.yml` gains a
   Postgres service on the `check-python` job and sets the test URL. The
   image's major version is the one Supabase runs for new projects at
   implementation time, named in the workflow with that reason.
10. **ADR-013 decision 5 is amended** to the text under Behavior, with an
    "Amended (spec 103)" note, as ADR-009 was amended by spec 041.
11. **`docs/architecture.md`** names the store URL, the `harrier store`
    commands, and spec 112 in its hosted section.

## Behavior

**Local, URL unset.** Every command, the API and the demo behave as today.
`harrier store status` prints `sqlite` and the version. `harrier store
migrate` on SQLite applies pending migrations, which an ordinary open
already does, and prints the version before and after.

**`harrier store migrate` with a Postgres URL.** On an empty database it
creates `schema_version`, applies the baseline, records version 9, and
prints `postgres 0 -> 9`. Run again, it prints `postgres 9 -> 9` and
changes nothing. Two runs started together apply the baseline once; the
second waits on the advisory lock and finds version 9.

**Opening a Postgres store behind the code.** `harrier store status`
prints the version and `behind: 9 expected` (or the current target).
Any other open of that store raises the refusal named under Failure modes.

**The parity test.** For each table, the two fresh stores have the same
column names in the same order, the same nullability, and unique
constraints over the same columns with the same partial predicate. A row
inserted with only its required columns gets defaults of the same shape
in both: empty strings equal, timestamps matching the same pattern. Then
a fixed list of probes runs against both, and each must be refused, or
accepted, in both:

| Probe | Expected |
|---|---|
| job with `status = 'bogus'` | refused |
| track slugs `Bad_Slug`, `1abc`, and 33 letters | refused |
| track slug `ok-1` | accepted |
| deadline `2026-1-01` | refused |
| deadline `''` and `2026-10-10` | accepted |
| `UPDATE` or `DELETE` on a `job_events` row | refused, message `job_events is append-only` |
| job with `track_id = 99` | refused |
| `DELETE` from `tracks` | refused, message `tracks are archived, never deleted` |
| `UPDATE tracks SET id = 5` | refused, message `a track id never changes` |
| event with `kind = 'outcome'` and `actor = 'candidate'` | refused |
| two jobs with the same non-empty `url` | second refused |
| two jobs with `url = ''` | both accepted |
| a track inserted without an id after the seed | accepted, id not 1 |
| a second `user_config` row with the same `kind` | refused |
| a second `profile_documents` row with the same `(kind, name)` | refused |

Where SQLite's message is the trigger's text and Postgres's is a foreign
key or check violation (the unknown track), the probe asserts refusal only.
Matching error classes and messages for callers is spec 112's.

**ADR-013 decision 5, amended text:**

> 5. **One write path, per dialect.** `harrier.tracker` stays the only
>    writer (ADR-003, ADR-012 point 4). The schema keeps one definition in
>    `services/api/src/harrier/tracker/schema.py`: each migration declares
>    its SQLite and Postgres statements together, Postgres history begins
>    with a baseline at the version the local schema had when the hosted
>    store was introduced, and a parity test holds the two to the same
>    tables, columns, defaults and refusals. The hosted-only columns and
>    policies are part of that definition, marked hosted. Migrations stay
>    harrier's own runner (spec 090) with a Postgres dialect. Supabase CLI
>    migrations are not used, because they would be a second schema
>    definition.
>
>    Amended (spec 103). This said SQLite and Postgres DDL "are produced"
>    from one definition. Nine migrations of SQLite history cannot be
>    regenerated without rewriting history, and a generator over triggers
>    and dialect functions is a second language to maintain. Declaring both
>    dialects in one entry, with a test that fails when they disagree, is
>    the property the sentence was for.

## Failure modes

- **Unsupported scheme.** `HARRIER_DATABASE_URL=mysql://...` or a bare
  path: every command and the API refuse with `error: HARRIER_DATABASE_URL
  must be empty or a postgresql:// URL`, exit 1. Nothing opens SQLite as a
  fallback.
- **psycopg not installed.** A Postgres URL without the `postgres` group:
  refused with a message naming `uv sync --group postgres`, exit 1.
- **Unreachable or rejected connection.** The error names the host and
  database and never the password or the full URL. A URL carries a
  credential, and spec 035 is the record of a credential leaking through
  an exception message. Proven by a test that connects with a known
  password to a closed port and asserts the password is absent from the
  message and from captured logs.
- **Store behind the code.** Any open other than `harrier store` raises
  `error: the Postgres store is at version N; this code needs M. Run
  harrier store migrate.`, exit 1. It does not migrate.
- **Store ahead of the code.** A store at a version higher than the code
  knows is refused the same way, naming both versions, on both dialects
  for `harrier store`; the SQLite open path keeps its current behavior.
- **A migration fails halfway.** The transaction rolls back; the version
  row is not written; the next run starts the same migration again.
  Proven on Postgres by the spec 090 broken-migration test, run against
  both dialects.
- **Two first migrations at once.** One applies the baseline; the other
  waits on the advisory lock, re-reads, and applies nothing.
- **A later migration with one dialect missing.** The test over
  `MIGRATIONS` fails, naming the version.
- **Postgres tests without Postgres.** Locally, with no test URL, the
  Postgres tests are skipped and pytest's summary says so. In CI
  (`CI=true`), a missing or unreachable test URL fails the run: a gate
  that skips in CI has not run (spec 039).
- **A data command with a Postgres URL.** Refused before it opens
  anything: `error: HARRIER_DATABASE_URL names a Postgres store; only
  harrier store runs on it until spec 112`, exit 1. The API refuses to
  start with the same text.

## Acceptance criteria

- [ ] With `HARRIER_DATABASE_URL` unset, the full suite passes with no
      test changed in behavior, and `just demo` starts as before.
- [ ] `harrier store migrate` on an empty Postgres database prints
      `postgres 0 -> 9`; a second run prints `postgres 9 -> 9` (planned
      test_migrate_applies_the_baseline_once).
- [ ] Two concurrent `harrier store migrate` runs leave one version row
      per version (planned test_two_first_migrations_apply_once_on_postgres).
- [ ] The parity test passes and fails when one Postgres column is
      renamed, one default changed, or one probe's constraint removed;
      the pull request records each of those three runs (planned
      test_both_dialects_build_the_same_tracker).
- [ ] Every probe in the Behavior table is asserted against both dialects.
- [ ] The spec 090 broken-migration test runs against both dialects.
- [ ] A migration after version 9 with an empty Postgres or SQLite list
      fails a test that names the version (planned
      test_every_new_migration_declares_both_dialects).
- [ ] A connection failure's message and logs do not contain the password
      (planned test_a_connection_failure_never_prints_the_password).
- [ ] An unsupported scheme, a missing driver, a store behind the code, and
      a data command with a Postgres URL each exit 1 with the text under
      Failure modes.
- [ ] CI's `check-python` job runs the Postgres tests, and fails when its
      Postgres service is removed (recorded in the pull request).
- [ ] ADR-013 decision 5 carries the amended text and note.
- [ ] `services/api/src/harrier/tracker/schema.py` is the only file holding
      Postgres DDL.
- [ ] `just check` passes.

## Honest limitations

- Nothing reads or writes tracker rows on Postgres after this spec. It
  proves the store exists and refuses what SQLite refuses; spec 112 makes
  the domain use it.
- The parity test compares shapes and a fixed list of refusals. A
  constraint added to one dialect and not named in the probes is caught
  only if it changes a column, a default or a unique constraint.
- Timestamps stay text in Postgres to keep every API value the same shape.
  Native timestamp types would sort and compare better; changing them
  changes the contract and is its own spec.
- Postgres `lower()` and SQLite `NOCASE` differ outside ASCII. That is a
  query concern for spec 112, named here because the baseline adds no
  case-insensitive collation.
- The baseline is written against the Postgres major version in CI. A
  Supabase project on another major version is spec 110's to check.

## Migration

None for the local product. A Postgres store is created only by
`harrier store migrate` and holds nothing until spec 112.

## Options weighed

- **SQLAlchemy Core as the definition and the access layer.** One
  `MetaData` generates DDL for both, and `text()` binds work on both. It
  replaces the stdlib driver everywhere, adds a large dependency to a
  service that has none for its database, and still needs hand-written
  triggers, so it is not one definition either. Not chosen.
- **Replay migrations 1 to 9 on Postgres.** Every SQLite workaround (the
  rebuild in 6, the triggers in 8) would become Postgres history for a
  store that never had the problem. Not chosen: the baseline records the
  shape, and the parity test proves it equal.
- **Migrate on open, as SQLite does.** Requests run as a role without DDL
  rights (ADR-013 decision 3), and a deploy should migrate once, not every
  machine on its first request. Not chosen.
- **One spec for the store and the domain port.** Every SQL call site, the
  error mapping and both-dialect tests for every reader in one change.
  Not chosen: spec 112 takes the domain.

## Open decisions for Akin

1. **Driver.** psycopg 3 in an optional `postgres` group (recommended), or
   SQLAlchemy Core (Options weighed).
2. **Postgres history.** A baseline at version 9 (recommended), or replay
   migrations 1 to 9 in Postgres dialect.
3. **Timestamps.** Text with SQLite's formats (recommended, no contract
   change), or native `timestamptz` with a contract change.
4. **Local Postgres tests.** Opt-in by test URL and required in CI
   (recommended), or `just check` starts a Postgres container itself.

## Out of scope

- Any domain read or write on Postgres, the error mapping, `COLLATE
  NOCASE`, `lastrowid`, and the `sqlite3.Connection` annotations: spec 112.
- `owner_id`, row-level policy, roles: spec 105.
- Authentication and the `authenticated` role: spec 104.
- Supabase projects, deploy order, who runs `harrier store migrate` in
  production: spec 110.
- Backup, `doctor --integrity`, cutover, legacy import and the host lease.
  They stay SQLite only; spec 112 states how each refuses on Postgres.
- Native timestamp types.
