# Spec 103: A Postgres store opens at the tracker's current schema

## Problem

The tracker exists only as SQLite. `services/api/src/harrier/tracker/schema.py`
holds nine migrations written in SQLite's dialect, `harrier.db.connect`
opens only `sqlite3`, and the migration runner (spec 090) takes SQLite's
write lock with `BEGIN IMMEDIATE`. ADR-013 decision 1 makes the hosted
store Supabase Postgres, and decision 5 requires one schema definition
for both dialects and harrier's own runner for both. Nothing can be built
on a hosted store until that store exists with the same tables and the
same refusals as the local one.

The SQLite DDL does not run on Postgres as written. Six constructs differ:

- `datetime('now')` and `strftime('%Y-%m-%dT%H:%M:%SZ', 'now')` defaults
  (`schema.py:162`, `:315` and four more tables).
- `GLOB` in the slug CHECK (`schema.py:356-357`) and the deadline CHECK
  (`schema.py:421`). ADR-012 point 5 already names a regular-expression
  CHECK as the Postgres form.
- `RAISE(ABORT, ...)` triggers: two make `job_events` append-only
  (`schema.py:335-341`), two stand in for the foreign key SQLite refuses on
  an added column (`schema.py:378-389`), two protect `tracks`
  (`schema.py:394-402`).
- `INTEGER PRIMARY KEY` as a rowid alias. Migration 8 inserts track `id = 1`
  explicitly (`schema.py:368-369`); a Postgres identity column does not
  advance its sequence for an explicit id, so the next default insert would
  collide with it.
- Migrations 5 and 6 rebuild or drop for SQLite reasons
  (`schema.py:262`, `:279-294`). Postgres never had the old shapes.
- `BEGIN IMMEDIATE` in the runner (`db.py:322`). Postgres needs its own
  way to make two first opens apply each migration once.

The rest of the domain (the write path, readers, upserts, `COLLATE NOCASE`,
`lastrowid`, `sqlite3.IntegrityError`) is out of this spec. It is SQL in
nine modules (`tracker/store.py`, `tracks.py`, `userconfig/store.py`,
`profile/store.py`, `runoutcome.py`, `mail/watch.py`, `logredact.py`,
`apply/profile.py`, `resume/content.py`) and the `sqlite3.Connection`
annotation in 39 more. 48 files match
`git grep -l 'sqlite3\.Connection' -- services/api/src | wc -l`, the nine
among them, counted 2026-10-10 on main after PR #219. That is spec 112.
Splitting here keeps each change reviewable against its spec, as
`change-boundary` asks.

## Scope

1. **The store URL.** `HARRIER_DATABASE_URL`, read from the environment.
   Unset or empty: the local SQLite store, exactly as today. A
   `postgresql://` URL: the Postgres store. Any other scheme is refused.
2. **The Postgres driver** is psycopg 3, in a new optional dependency
   group `postgres` in `services/api/pyproject.toml`, like the `pdf` group.
   A local install without it is unchanged.
3. **Migrations declare both dialects together.** Each entry in
   `MIGRATIONS` carries its SQLite statements and its Postgres statements.
   Migrations 1 to 9 keep their SQLite statements unchanged and carry no
   Postgres statements. A Postgres baseline, recorded as version 9, creates
   the schema that SQLite reaches after migration 9. Every migration after
   9 must carry both lists; a test fails if one is empty.
4. **The Postgres baseline** maps each construct listed under Problem:
   - `id` columns are `bigint generated by default as identity primary
     key`. After seeding track 1, the baseline advances the `tracks`
     sequence past it.
   - Timestamp defaults produce the same text formats SQLite produces:
     `YYYY-MM-DD HH:MM:SS` in UTC where SQLite uses `datetime('now')`, and
     `YYYY-MM-DDTHH:MM:SSZ` for `job_events.at`. Columns stay `text`, so no
     value read through the API changes shape.
   - The slug CHECK is `slug ~ '^[a-z][a-z0-9-]{0,31}$'`. The deadline
     CHECK is `deadline = '' OR deadline ~ '^[0-9]{4}-[0-9]{2}-[0-9]{2}$'`.
   - `jobs.track_id` is a real foreign key to `tracks(id)`. The two
     SQLite triggers that stand in for it have no Postgres counterpart.
   - `job_events` append-only, tracks never deleted, and a track id never
     changing are PL/pgSQL trigger functions raising the same message
     texts the SQLite triggers raise.
   - Partial unique indexes on `jobs.url` and `jobs.external_key`, the
     CHECKs on `status`, `tracks.kind`, `job_events.kind`, `actor`,
     `backfilled` and the outcome/company rule are written as in SQLite.
5. **The runner speaks both.** `_apply_schema` runs Postgres migrations
   each inside one transaction (Postgres DDL is transactional, so spec
   090's whole-or-nothing rule holds), after taking a transaction-scoped
   advisory lock and re-reading the version under it, the Postgres
   counterpart of `BEGIN IMMEDIATE`.
6. **Opening a Postgres store never migrates it.** ADR-013 decision 3
   gives requests a role that cannot run DDL. Opening checks the store's
   version and refuses if it is behind the code. Migration is one explicit
   command: `harrier store migrate`, which applies pending migrations to
   the store `HARRIER_DATABASE_URL` names and prints the version before
   and after. `harrier store status` prints the dialect and version.
7. **Nothing else uses the Postgres store yet.** Until spec 112, every API
   start and every CLI command except `harrier store` refuses to run while
   `HARRIER_DATABASE_URL` names a Postgres store, so no process silently
   uses SQLite while the operator believes it uses Postgres.
8. **The parity test** opens a fresh SQLite store and a fresh Postgres
   store and compares them (see Behavior).
9. **CI runs the Postgres tests.** `.github/workflows/ci.yml` gains a
   Postgres service on the `check-python` job and sets the test URL. The
   image's major version is the one Supabase runs for new projects at
   implementation time, named in the workflow with that reason.
10. **ADR-013 decision 5 is amended** to the text under Behavior, with an
    "Amended (spec 103)" note, as ADR-009 was amended by spec 041.
11. **`docs/architecture.md`** names the store URL, the `harrier store`
    commands, and spec 112 in its hosted section.

## Behavior

**Local, URL unset.** Every command, the API and the demo behave as today.
`harrier store status` prints `sqlite` and the version. `harrier store
migrate` on SQLite applies pending migrations, which an ordinary open
already does, and prints the version before and after.

**`harrier store migrate` with a Postgres URL.** On an empty database it
creates `schema_version`, applies the baseline, records version 9, and
prints `postgres 0 -> 9`. Run again, it prints `postgres 9 -> 9` and
changes nothing. Two runs started together apply the baseline once; the
second waits on the advisory lock and finds version 9.

**Opening a Postgres store behind the code.** `harrier store status`
prints the version and `behind: 9 expected` (or the current target).
Any other open of that store raises the refusal named under Failure modes.

**The parity test.** For each table, the two fresh stores have the same
column names in the same order, the same nullability, and unique
constraints over the same columns with the same partial predicate. A row
inserted with only its required columns gets defaults of the same shape
in both: empty strings equal, timestamps matching the same pattern. Then
a fixed list of probes runs against both, and each must be refused, or
accepted, in both:

| Probe | Expected |
|---|---|
| job with `status = 'bogus'` | refused |
| track slugs `Bad_Slug`, `1abc`, and 33 letters | refused |
| track slug `ok-1` | accepted |
| deadline `2026-1-01` | refused |
| deadline `''` and `2026-10-10` | accepted |
| `UPDATE` or `DELETE` on a `job_events` row | refused, message `job_events is append-only` |
| job with `track_id = 99` | refused |
| `DELETE` from `tracks` | refused, message `tracks are archived, never deleted` |
| `UPDATE tracks SET id = 5` | refused, message `a track id never changes` |
| event with `kind = 'outcome'` and `actor = 'candidate'` | refused |
| two jobs with the same non-empty `url` | second refused |
| two jobs with `url = ''` | both accepted |
| a track inserted without an id after the seed | accepted, id not 1 |
| a second `user_config` row with the same `kind` | refused |
| a second `profile_documents` row with the same `(kind, name)` | refused |

Where SQLite's message is the trigger's text and Postgres's is a foreign
key or check violation (the unknown track), the probe asserts refusal only.
Matching error classes and messages for callers is spec 112's.

**ADR-013 decision 5, amended text:**

> 5. **One write path, per dialect.** `harrier.tracker` stays the only
>    writer (ADR-003, ADR-012 point 4). The schema keeps one definition in
>    `services/api/src/harrier/tracker/schema.py`: each migration declares
>    its SQLite and Postgres statements together, Postgres history begins
>    with a baseline at the version the local schema had when the hosted
>    store was introduced, and a parity test holds the two to the same
>    tables, columns, defaults and refusals. The hosted-only columns and
>    policies are part of that definition, marked hosted. Migrations stay
>    harrier's own runner (spec 090) with a Postgres dialect. Supabase CLI
>    migrations are not used, because they would be a second schema
>    definition.
>
>    Amended (spec 103). This said SQLite and Postgres DDL "are produced"
>    from one definition. Nine migrations of SQLite history cannot be
>    regenerated without rewriting history, and a generator over triggers
>    and dialect functions is a second language to maintain. Declaring both
>    dialects in one entry, with a test that fails when they disagree, is
>    the property the sentence was for.

## Failure modes

- **Unsupported scheme.** `HARRIER_DATABASE_URL=mysql://...` or a bare
  path: every command and the API refuse with `error: HARRIER_DATABASE_URL
  must be empty or a postgresql:// URL`, exit 1. Nothing opens SQLite as a
  fallback.
- **psycopg not installed.** A Postgres URL without the `postgres` group:
  refused with a message naming `uv sync --group postgres`, exit 1.
- **Unreachable or rejected connection.** The error names the host and
  database and never the password or the full URL. A URL carries a
  credential, and spec 035 is the record of a credential leaking through
  an exception message. Proven by a test that connects with a known
  password to a closed port and asserts the password is absent from the
  message and from captured logs.
- **Store behind the code.** Any open other than `harrier store` raises
  `error: the Postgres store is at version N; this code needs M. Run
  harrier store migrate.`, exit 1. It does not migrate.
- **Store ahead of the code.** A store at a version higher than the code
  knows is refused the same way, naming both versions, on both dialects
  for `harrier store`; the SQLite open path keeps its current behavior.
- **A migration fails halfway.** The transaction rolls back; the version
  row is not written; the next run starts the same migration again.
  Proven on Postgres by the spec 090 broken-migration test, run against
  both dialects.
- **Two first migrations at once.** One applies the baseline; the other
  waits on the advisory lock, re-reads, and applies nothing.
- **A later migration with one dialect missing.** The test over
  `MIGRATIONS` fails, naming the version.
- **Postgres tests without Postgres.** Locally, with no test URL, the
  Postgres tests are skipped and pytest's summary says so. In CI
  (`CI=true`), a missing or unreachable test URL fails the run: a gate
  that skips in CI has not run (spec 039).
- **A data command with a Postgres URL.** Refused before it opens
  anything: `error: HARRIER_DATABASE_URL names a Postgres store; only
  harrier store runs on it until spec 112`, exit 1. The API refuses to
  start with the same text.

## Honest limitations

- Nothing reads or writes tracker rows on Postgres after this spec. It
  proves the store exists and refuses what SQLite refuses; spec 112 makes
  the domain use it.
- The parity test compares shapes (columns, types, nullability,
  defaults, unique constraints, foreign keys) and a fixed list of refusals
  and acceptances. A CHECK or trigger added to one dialect and not reached
  by a probe is not caught. TRUNCATE has no SQLite counterpart, so no
  probe that runs on both stores can test it; spec 105 refuses it on
  Postgres.
- A connection error's traceback still holds the frame of
  `postgres_connect`, whose locals include the URL. An error reporter that
  records local variables would see the password. None is configured;
  spec 110 decides the hosted one.
- Timestamps stay text in Postgres to keep every API value the same shape.
  Native timestamp types would sort and compare better; changing them
  changes the contract and is its own spec.
- Postgres `lower()` and SQLite `NOCASE` differ outside ASCII. That is a
  query concern for spec 112, named here because the baseline adds no
  case-insensitive collation.
- The baseline is written against the Postgres major version in CI. A
  Supabase project on another major version is spec 110's to check.

## Migration

None for the local product. A Postgres store is created only by
`harrier store migrate` and holds nothing until spec 112.

## Options weighed

- **SQLAlchemy Core as the definition and the access layer.** One
  `MetaData` generates DDL for both, and `text()` binds work on both. It
  replaces the stdlib driver everywhere, adds a large dependency to a
  service that has none for its database, and still needs hand-written
  triggers, so it is not one definition either. Not chosen.
- **Replay migrations 1 to 9 on Postgres.** Every SQLite workaround (the
  rebuild in 6, the triggers in 8) would become Postgres history for a
  store that never had the problem. Not chosen: the baseline records the
  shape, and the parity test proves it equal.
- **Migrate on open, as SQLite does.** Requests run as a role without DDL
  rights (ADR-013 decision 3), and a deploy should migrate once, not every
  machine on its first request. Not chosen.
- **One spec for the store and the domain port.** Every SQL call site, the
  error mapping and both-dialect tests for every reader in one change.
  Not chosen: spec 112 takes the domain.

## Open decisions for Akin

Akin took the recommended answer to each on 2026-10-10. Scope and
Behavior above already describe these answers.

1. **Driver: psycopg 3** in an optional `postgres` group. SQLAlchemy Core
   was the alternative (Options weighed).
2. **Postgres history: a baseline at version 9.** Replaying migrations 1 to
   9 in Postgres dialect was the alternative.
3. **Timestamps: text in SQLite's formats,** so no contract change. Native
   `timestamptz` would change the contract and is its own spec if wanted.
4. **Postgres tests: opt-in locally by test URL, required in CI.** Having
   `just check` start a Postgres container was the alternative.

## Amendment (2026-10-10, during implementation)

- **The Postgres statements are a parallel list, not a field of each
  entry (Scope item 3).** `MIGRATIONS` stays a list of `(version,
  statements)` pairs. The SQLite runner in `harrier/db.py` and six
  existing test files (`test_migration_runner.py`, `test_runs.py`,
  `test_scoring.py`, `test_tracker_invariants.py`, `test_tracks.py`,
  `test_userconfig.py`) unpack it in that shape, and a third field on every
  entry would have changed all of them for no change in behavior. The
  Postgres side is `POSTGRES_MIGRATIONS` in the same module,
  `services/api/src/harrier/tracker/schema.py`. `undeclared_dialects`
  holds the two lists together: every version after the baseline must
  appear in both with at least one statement, and a test names the
  version that does not
  (`services/api/tests/test_postgres_store.py::test_every_new_migration_declares_both_dialects`).
  The property Scope item 3 asks for is the same; only the layout differs.
- **The Postgres runner lives in `harrier/pgstore.py`, not in
  `_apply_schema` (Scope item 5).** It is
  `harrier.pgstore.apply_postgres_migrations`. Kept out of `harrier.db`,
  the SQLite open path never imports psycopg, so a local install without
  the `postgres` group opens SQLite exactly as before. The runner takes the
  advisory lock and re-reads the version inside each migration's
  transaction, as Scope item 5 states.
- **psycopg is installed for tests.** It is the optional `postgres` group in
  `services/api/pyproject.toml`, and the dev group includes that group, so
  `uv sync` in development and CI installs it and the Postgres tests can
  run.
- ADR-013 decision 5 records both layout changes beside its amended text.
- **One difference the baseline cannot close: `job_runs.job` may be NULL
  on SQLite.** It is `TEXT PRIMARY KEY` without `NOT NULL`, and SQLite
  allows NULL in such a key; a Postgres primary key never does. The parity
  test names this one difference in `KNOWN_NULLABILITY_DIFFERENCES` and
  proves it is real
  (`services/api/tests/test_dialect_parity.py::test_the_known_difference_is_real`),
  so any other nullability difference still fails. Closing it is a SQLite
  migration that rebuilds `job_runs`, which changes the local schema and
  needs its own spec.
- **The local image does not install the `postgres` group.**
  `services/api/tests/test_container.py` requires every optional group to be
  installed in the image or named as excluded. It is named in
  `NOT_IN_THE_LOCAL_IMAGE`: the local container runs on SQLite, Scope item 2
  keeps a local install unchanged, and the hosted image is spec 110's.
- **`harrier store` skips logging setup on both dialects.** Logging setup
  opens SQLite through `connect`, which migrates, so `store migrate` would
  always have printed `N -> N`. On SQLite `store status` reads the file
  without writing and prints no `behind:` line, since any ordinary open
  migrates it.
- **The refusal text is one constant,** `harrier.connection.POSTGRES_NOT_YET`,
  used by the CLI and the API. (It was `harrier.pgstore.POSTGRES_NOT_YET`
  until spec 112's PR 1 moved it, 2026-10-11.)
- **"A store behind the code" is refused where a store is opened for use,**
  by `harrier.pgstore.open_postgres_store`
  (`services/api/tests/test_postgres_store.py::test_opening_an_unmigrated_store_is_refused`).
  No CLI command opens one for use until spec 112, so no command exits 1
  for it yet; `harrier store status` reports it instead.

## Corrections after the post-merge review (2026-10-10)

PR #207 merged with no review, because the review service was rate
limited. A review run afterwards found these, corrected here and in the
same change's code:

- **The API now reads the URL from `.env` too.** The CLI loads `.env`; the
  API did not, so a URL set only there made the CLI refuse while the API
  served SQLite, the case Scope item 7 exists to prevent.
  `harrier.connection.store_target` reads the variable from the environment
  and, when it is not set there, from `.env`, through the CLI's own parser
  (`services/api/src/harrier/envfile.py`). (It was
  `harrier.pgstore.store_target` until spec 112's PR 1 moved it,
  2026-10-11.) An exported value, even empty, wins
  (`services/api/tests/test_store_cli.py::test_a_url_in_dotenv_reaches_the_api_as_it_reaches_the_cli`,
  `services/api/tests/test_store_cli.py::test_an_exported_value_wins_over_dotenv_for_the_api_too`).
- **The scrub covers the encoded password.** libpq quotes a URL it refuses
  as written, still percent-encoded; the scrub replaced only the decoded
  form, so a password with an invalid escape was printed whole. The two
  earlier password tests connect to a closed port, whose message never
  quotes the password, so they passed with the scrub removed. The driver's
  error also stayed chained as `__context__` despite `from None`, holding
  the password; the refusal is now raised after the `except` block, so
  nothing is chained
  (`services/api/tests/test_postgres_store.py::test_a_driver_error_that_quotes_the_password_never_carries_it`).
- **`StoreTarget` no longer shows its URL in its repr**
  (`services/api/tests/test_postgres_store.py::test_a_store_target_never_shows_its_password`).
- **A malformed URL is refused like any other.** A bad port or host raised
  a bare `ValueError`, and a scheme in another case passed here and failed
  in libpq with an unrelated message
  (`services/api/tests/test_postgres_store.py::test_a_malformed_url_is_refused_like_any_other`).
- **A migration the server refuses exits 1 with one line.** A
  `psycopg.Error` from a migration's statement escaped `harrier store
  migrate` as a driver traceback. It now prints `error: a migration
  failed: <the server's primary message>` and exits 1. That message
  quotes SQL, never the URL
  (`services/api/tests/test_store_cli.py::test_a_failed_migration_exits_1_with_the_drivers_message`).
- **Tests never read an operator's URL.** `services/api/tests/conftest.py`
  sets `HARRIER_DATABASE_URL` empty for the session and for every test, so
  a hosted URL in the operator's shell or `.env` cannot reach the suite
  (spec 060). Without it, a run started beside such a `.env` fails at
  collection.
- **Two acceptance boxes said more than was proven.** "A store behind the
  code exits 1" contradicted the Amendment; it is reworded to what holds.
  "Fails when its Postgres service is removed" was ticked in PR #209 on a
  passing CI run and a local stand-in; it is reworded to say so.
- **The amended text quoted under Behavior is the proposal.** The text that
  landed is `docs/adr/ADR-013-hosted-multi-tenant-deployment.md` decision
  5, which says the dialects are held to the same versions in one module
  rather than "in one entry", and that this applies to each migration
  after the baseline.

### Fourth review, of PR #231 (2026-10-11)

Two reviews of the corrections above, after PR #231 merged, found these,
corrected in the change that adds this list:

- **A `#`, tab, CR or LF in the URL leaked the password.** The scrub
  learns the password from urlsplit, which reads a raw `#` as the start
  of a fragment and drops a raw tab, CR or LF. libpq does neither: it
  takes the whole text as the password and quotes it when an escape in it
  is invalid. With `?password=x#<secret>%zz` the scrub replaced only the
  `x`; with a tab in the password it replaced nothing.
  `harrier.connection.store_target` (in `harrier.pgstore` until spec
  112's PR 1 moved it) now refuses a URL holding any of the four, with the same message as any malformed URL and nothing chained. A
  written URL carries them percent-encoded
  (`services/api/tests/test_postgres_store.py::test_a_malformed_url_is_refused_like_any_other`,
  `services/api/tests/test_postgres_store.py::test_a_url_urlsplit_reads_differently_from_libpq_never_reaches_the_cli`).
  The review also offered deriving scrub forms from libpq's own parse
  (`psycopg.conninfo.conninfo_to_dict`). Not done in this change: in
  every case that leaked, the escape that made libpq quote the password
  also made that parse fail. The privacy review of PR #243 (below) used
  that same failure as the refusal, and added the forms as a second
  line.
- **A valid URL with an `@` in its query was refused.** The `@` rule
  counted every `@` before the first `/`, so
  `postgresql://u:p@host?application_name=a@b`, which libpq and urlsplit
  read alike, was refused. libpq looks for the user's `@` up to the first
  `/` and stops at the first one; urlsplit takes the last one before the
  first `/`, `?` or `#`. `store_target` now refuses only when they split
  at different `@`s, or one finds an `@` and the other none
  (`services/api/tests/test_postgres_store.py::test_an_at_sign_in_the_query_after_the_host_is_accepted`).

  `services/api/tests/test_postgres_store.py::test_an_at_sign_libpq_reads_as_the_host_never_reaches_the_cli`).
- **The pin net had gaps.** A marked `dotenv_fallback` test that unset
  the pin outside its `tmp_path` had no case. The record of the pin at

  removed. That branch was wrongly called unreachable here: it caught a
  pin removed with no audit event, and the review of PR #243 restored
  it (below). And an unset before the
  net's per-test watch opened, as in a module-scoped fixture or an import

### Privacy review and claims audit of PR #243 (2026-10-11)

A privacy review and a claims audit of the fourth review's change, before
it merged, found these, corrected in the same pull request:

- **libpq's own text reached the CLI.** libpq quotes the text of a URL it
  cannot parse: a query parameter without its `=` (`?password:<S>`,
  `?password%3D<S>`, `?password <S>`) whole, an invalid escape in any
  parameter, and for an unclosed `[` host the whole URL, which this spec
  forbids. A value that is not UTF-8 once decoded (`%FF`, a truncated
  `%C3`, a raw byte) crashed with a traceback giving the password's
  length. `harrier.connection.store_target` now also parses the URL with
  libpq's own parser (`psycopg.conninfo.conninfo_to_dict`, imported only
  when a Postgres URL is read) and refuses it, with harrier's
  malformed-URL message alone and nothing chained, when that parse fails
  in any way, a decode or encode error included
  (`services/api/tests/test_postgres_store.py::test_a_url_libpq_cannot_parse_never_reaches_the_cli`).
  Without psycopg the parse is skipped; every command that would connect
  refuses for the missing driver first. Each URL the fourth review's `#`,
  tab, CR and LF refusal was tested with is refused by this parse as
  well: with that refusal removed, every test passes. It stays as a
  second line, because it also refuses a URL urlsplit misreads that libpq
  parses; no such URL was found that leaks without it.
- **Other secret parameters were never scrubbed.** libpq takes
  `sslpassword` and `oauth_client_secret` from the query too. The scrub
  (`harrier.pgstore._scrub`, fed by `harrier.connection.url_parts`) now
  learns every query parameter whose decoded name holds `pass` or
  `secret`
  (`services/api/tests/test_postgres_store.py::test_every_secret_parameter_is_scrubbed`).
  It also learns those values from libpq's parse when it succeeds. That
  is a second line: removing it passes every test, because each URL that
  makes libpq quote a secret is one its parser refuses.
- **Overlapping forms left part of a secret.** The scrub replaced the
  longest form first; a shorter form overlapping it lost its match, and
  its other part, ten characters of the password, was printed. The scrub
  now finds every occurrence of every form in the text as written and
  replaces the union of their spans
  (`services/api/tests/test_postgres_store.py::test_two_overlapping_secrets_are_both_scrubbed`).
- **A failure outside psycopg's classes escaped
  `harrier.pgstore.postgres_connect`.** A
  decode or encode error, and urlsplit's error on a port it cannot read,
  which quotes the text it read as the port, were tracebacks the CLI does
  not catch. Every failure to connect is now a `StoreConnectionError`
  naming only the error's class, or saying the URL is malformed, with
  nothing chained
  (`services/api/tests/test_postgres_store.py::test_any_failure_to_connect_is_a_store_error`).
- **The pin net missed losses with no unset event.** The fourth review
  removed the end-of-test branch that caught them. Deleting from
  `os.environ._data`, or replacing `os.environ` with a mapping that lacks
  the pin, raises no `os.unsetenv` event; and a child started with an
  `env` that leaves the pin out loads `.env` from its own working
  directory. The net now fails a test that ends with the pin absent and
  no unset recorded, records the CLI's `.env` loader writing the pin as
  losing it (the loader writes only an absent key), and records a child
  started through `subprocess` with an `env` lacking the pin, at the
  child's working directory
  (`services/api/tests/test_store_cli.py::test_the_pin_net_fails_a_test_that_dropped_the_pin_whatever_it_holds_after`).
  The audit asked that the pin also be the empty string at the end of a
  test. Not done: the Postgres tests set their own URL through
  `monkeypatch`, and the case it would catch, `.env` writing the pin
  back, is the loader's write, which the net now sees.

#### Honest limitations (privacy review of PR #243)

- **Single-host URLs only.** This spec names one store, one host. A
  multi-host URL whose first host carries a port
  (`postgresql://u:p@h1:5432,h2:5433/db`,
  `postgresql://u:p@[::1]:5432,[::2]:5433/db`) is refused: urlsplit
  cannot read `5432,h2` as a port. `postgresql://u:p@h1,h2:5433/db` is
  accepted, and the error text names the host as `h1,h2`. A password
  holding a fullwidth `＠` or `：` is refused, because urlsplit refuses
  characters that normalize to a separator; so is a port above 65535,
  which libpq would read. Widening what is accepted is not done here.
- **The pin net sees the paths named above.** A test that replaces
  `os.environ` and restores it before the test ends, as a `mock.patch`
  context inside the test body does, is not seen; nor is a child started
  through `os.posix_spawn` or an `os.exec*` call with its own
  environment.
- **A test that calls `main()` loads `.env` from the working
  directory.** `load_project_env` copies every key in that `.env` into
  `os.environ`, other keys than the pin included, and nothing restores
  them. Run from the repository root of a checkout with a real `.env`,
  the suite loads the operator's keys into the test process. `just
  check` runs pytest from `services/api`, where the repository keeps no
  `.env`, so the gate does not. Not fixed here: the loader always reads
  `.env` in the working directory (spec 011), and no setting points it
  elsewhere, so a fix changes the CLI's loader, not only the tests.
