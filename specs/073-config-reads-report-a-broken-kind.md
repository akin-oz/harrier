# Spec 073: The config routes report a broken kind instead of answering 500

## Problem

The config API (spec 023) answers 500 whenever reading one configuration
kind raises `ConfigError`. Two things raise it:

1. **A stored row that is not valid.** `get_config`
   (`services/api/src/harrier/userconfig/store.py`) validates on the way out
   as well as the way in, so a row written around `set_config` (a
   hand-edited database, a restored backup, a future migration) is refused
   on read. That refusal is deliberate (review finding on PR #20) and stays.
2. **A malformed `hold_until` in the company holds CSV.** Since spec 052 the
   file fallback refuses a bad date rather than reading it as "no expiry".
   That is also deliberate and stays.

The refusal is right. What the API does with it is not. `_config_out`
(`services/api/src/harrier_api/app.py`) does not catch `ConfigError`, so it
reaches FastAPI as an unhandled exception. Observed on 2026-10-04 with a
throwaway test against `create_app()`:

| Broken input | Route | Answer |
|---|---|---|
| stored `feeds` row `[7]` | `GET /config` | 500 |
| stored `feeds` row `[7]` | `GET /config/feeds` | 500 |
| stored `feeds` row `[7]` | `GET /config/discovery` | 200 |
| stored `feeds` row `[7]` | `PUT /config/feeds` with a valid list | 200 |
| holds CSV with `hold_until` `soon` | `GET /config` | 500 |
| holds CSV with `hold_until` `soon` | `GET /config/company_holds` | 500 |
| holds CSV with `hold_until` `soon` | `DELETE /config/company_holds` | 500, and the stored row **was** deleted |

So, for whoever reads configuration through the API:

- **One broken kind hides all four.** `GET /config` cannot list the healthy
  kinds because one of them is broken.
- **The answer does not say what is wrong.** A 500 carries no detail; the
  `ConfigError` message that names the field, the company and the file is
  in the server log only.
- **A delete that succeeded reports failure.** `DELETE` removes the row and
  then reads the fallback to build its response. When the fallback is
  broken, the client is told the delete failed and may retry or give up on
  a change that already happened.

Spec 052 records this under Limitations. The web app does not call `/config`
today (no reference under `apps/web/src`), so the consumers are API clients
and the generated contract.

## Scope

- `ConfigOut` and `_config_out` in `services/api/src/harrier_api/app.py`,
  which every config route answers through.
- The generated contract: `packages/contract/openapi.json` and
  `packages/contract/src/schema.d.ts`, regenerated by `just contract`, never
  hand-edited (ADR-005).
- Tests in `services/api/tests/test_userconfig.py`.
- `specs/052-hold-expiry.md`: its Limitations entry is replaced by a pointer
  to this spec.

The store, the accessors, discovery and the CLI do not change.

## Behavior

`ConfigOut` gains one field:

- `error: str | null`. Null when the kind's value was read. Otherwise the
  `ConfigError` message, verbatim, and `value` is null.

When reading a kind raises `ConfigError`, the config routes describe the
kind instead of failing:

- **`source` says where the broken value lives.** `store` when a row for
  the kind exists, whether or not it parses; `file` otherwise.
  `updated_at` is the row's timestamp when the source is `store`, as today.
- **A broken stored row does not fall back to the file.** The answer is
  `source: store` with the error, never the file's value. Falling back
  would show a value that discovery does not use, because discovery reads
  the same row and fails on it.
- **`GET /config`** answers 200 and lists every kind. Healthy kinds are
  unchanged; each broken kind carries its own `error`.
- **`GET /config/{kind}`** answers 200 with the broken kind's `error`.
- **`DELETE /config/{kind}`** deletes the row, then answers 200 describing
  what is now in effect. If the fallback is broken, that answer carries the
  fallback's `error`. A completed delete is never reported as a failure.
- **`PUT /config/{kind}`** is unchanged: a value its kind refuses answers
  400 with the store's message, and nothing is written. After a successful
  PUT the kind reads back with `error: null`, because the value was just
  validated.
- The 404 for an unknown kind is unchanged on every verb.

Only `ConfigError` is described this way. Any other exception (a database
error, an unreadable file) still answers 500, because those are not "this
kind's value is wrong" and are outside this spec.

## Options weighed

**Recommended: the error in the body, status 200.** The list route has to
answer for four kinds at once, and a status code describes the whole
response, so the list needs a per-kind field whatever the single-kind route
does. Using the same field on the single-kind route keeps one shape for one
question. It also lets the client show the broken kind next to the PUT that
repairs it, which is the only fix the API offers.

**Alternative: a status code on the single-kind route.** `GET
/config/{kind}` would answer 409 with `ConfigErrorOut`, and only the list
would carry `error`. It is closer to what a client checking only the status
expects. It gives the same kind two shapes depending on the route, and it
does not fix `DELETE`, which needs a 200 after a successful delete either
way.

The cost of the recommendation: a client that checks only the status code
reads a broken kind as healthy. `error` is a declared, nullable field in the
generated types, so a typed client sees it.

## Failure modes

- **Two kinds broken at once:** both are listed, each with its own `error`;
  the healthy kinds still read.
- **A stored row that is not valid JSON**, and one that is valid JSON of the
  wrong shape: both are `source: store` with `error`. The messages differ,
  as `get_config` writes them.
- **A stored `company_holds` row with a malformed date**, written around
  `set_config`: `source: store` with the error naming the company.
- **`DELETE` on a kind with no stored row and a broken fallback:** answers
  200 with the fallback's `error`. It answers 500 today.
- **`PUT` on one kind while another is broken:** unaffected, as today.
- **The kind is repaired:** the next read has `error: null` and the value.
  Nothing is cached.

## Data and privacy

`error` can name a company from the hold list (spec 052's message does).
That is the operator's own data, returned to the operator's own local API,
the same text the CLI already prints on `config import`. It is not logged by
this change. Tests use synthetic company names.

## Limitations

- **A status-only client sees 200.** See Options weighed.
- **Only `ConfigError` is covered.** A database error or an unreadable file
  during a config read still answers 500.

## Proof / origin

Spec 052's Limitations entry, written when implementing spec 052 (PR #104)
showed the 500 on a malformed holds CSV. The table in Problem was produced on 2026-10-04 by a
throwaway pytest file driving `create_app()` against a temporary data
directory, deleted after the run. The unguarded call is `_config_out` in
`services/api/src/harrier_api/app.py` as of commit 95a9eb4.

## Out of scope

- The CLI. `harrier config get` already prints the `ConfigError` and exits
  1.
- Discovery. It still fails loudly on a broken kind (spec 052); describing
  the error is for the config surface only.
- Repairing or deleting broken values automatically.
- A config page in the web app.
- Other exceptions during a config read (database errors, unreadable or
  undecodable files).
- Typing `value` per kind in the contract; it stays untyped JSON.

## Migration

None. Existing clients see one new nullable field, null on every healthy
kind.
