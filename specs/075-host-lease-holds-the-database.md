# Spec 075: A host lease keeps the container out while a host run holds the database

Split from the 2026-09-18 draft of spec 061 on 2026-10-04.

## Problem

Spec 061's check runs before a host process opens the database. It cannot see
the future. A host run starts while the container is down (for example during
`just container-up`, which recreates it), passes the check, opens the file,
and the container comes back mid-run and opens the same file. Two kernels
again, which is the configuration that corrupted the file on 2026-09-18.

With the launchd schedule installed (spec 074), gmail-watch fires every 300
seconds, so a run in flight while the container restarts is reachable in
normal use, not a corner case.

Nothing on the container side knows a host process holds the file, and
nothing in the API or the web app could say so.

## Scope

- `services/api/src/harrier/db.py`: the lease, and the container-side check
  in the guarded open.
- `services/api/src/harrier_cli/main.py`: the second engine query after the
  lease, and the lease lines in `harrier doctor`.
- `services/api/src/harrier_api/app.py`: the 503, its models, and the
  `/health` fields.
- The generated contract: `packages/contract/openapi.json` and
  `packages/contract/src/schema.d.ts`, regenerated by `just contract`.
- `apps/web/src/features/health/HealthBadge.tsx` and its test. No other web
  file.
- Tests under `services/api/tests/`.

## Behavior

### The lease

- Before a host process opens the live file it creates
  `data/host-db-owners/<pid>.json` (atomic exclusive create), then queries the
  engine, then opens. It removes the file on exit, normal or exceptional.
  Several host processes may hold leases at once; they share a kernel, which
  is the supported case.
- A lease holds exactly three values: the pid, the process start time, and
  the subcommand name as the parser knows it (for example `contacts
  approve`). It never holds an argument value. CLI arguments carry contact
  names, profile URLs and free text, and the lease is echoed by the API and by
  `harrier doctor`. A host process that is not the CLI records the subcommand
  as `python`.
- If the query that follows the lease says the container owns the file, or
  that ownership is unknown, the process removes its own lease, then
  delegates (a `database` command, spec 074) or refuses with exit 75. A
  refusal never leaves a lease behind.
- A delegating process never takes a lease, so the process it starts inside
  the container is not refused by one.

### Liveness

- A lease is live only when a process with that pid exists and its start time
  matches the recorded one. A pid reused by an unrelated process is dead for
  this purpose.
- A file named for the current process's own pid that the process did not
  write is stale by definition and is replaced.
- Any host invocation removes dead leases before it decides anything. With
  gmail-watch on its cadence, a lease left by a crashed host process is
  cleared within one interval.
- The container cannot judge whether a host pid is alive. It treats every
  lease file as live.
- `data/host-db-owners/` is covered by `data/**` in
  `config/data-classification.json` (never-in-git). No classification change.

### The container side

- Inside the container, every open of the live file first checks
  `data/host-db-owners/`. While any lease file exists the open raises
  `DatabaseOwnedByHost`.
- Checking at open time is enough. A lease can coexist with a running
  container only when the container started after the host's engine query, and
  a container that has just started holds no connection from before the
  lease.

### What the API says

Two models, exported to the contract (ADR-005):

- `DatabaseHoldOut`: `subcommand: str`, `since: str` (ISO 8601, UTC). With
  several leases it describes the oldest.
- `DatabaseHeldOut`: `detail: str` (a fixed sentence) and
  `hold: DatabaseHoldOut`.

A FastAPI exception handler maps `DatabaseOwnedByHost` to 503 with a
`DatabaseHeldOut` body. The 503 is declared the way this repository declares
error responses: one shared dictionary, merged into `responses=` on every
route whose handler depends on `Conn` (`services/api/src/harrier_api/deps.py`),
in the style of `CONFIG_ERRORS` and `TOKEN_RESPONSES`. That is most routes,
and the contract diff is that wide.

`/health` is the exception, because the compose healthcheck reads it and a
host run must not mark the container unhealthy. `HealthOut` has `database:
str` and `job_count: int` today. Both names stay.

- `/health` checks for a lease before it opens anything. With a lease present
  it does not open the database.
- New field `database_hold: DatabaseHoldOut | None`, null when no lease
  exists.
- `job_count` becomes `int | None`, null exactly when `database_hold` is set.

Runs started from the web app are subprocesses whose stderr becomes log lines
(`services/api/src/harrier_api/runs.py`). A run refused by a lease ends with
exit code 75 and the refusal sentence as a log line. `RunOut` is unchanged.

### The web app

`HealthBadge` renders `job_count` today and must handle `null`. It is where
the hold is shown: the subcommand and since when. Other pages show the 503
through the error rendering they already have, which prints the body
including `detail`.

### `harrier doctor`

Gains, after spec 061's lines: host leases, their count, and for each the
pid, subcommand name, start time, and whether it is live. It exits 1, in
addition to spec 061's cases, for a lease with a dead pid and for the
container running while a live host lease exists.

## Failure modes

- **Container starts during a host run.** The container's opens fail with 503
  until the host run ends. The badge shows the hold. `/health` stays 200.
- **Container starts between the CLI's first engine query and its first
  open.** The second query, made while holding the lease, sees it. The lease
  is removed and the command is delegated or refused.
- **A pid is reused.** By an unrelated process: the start time does not
  match, the lease is dead, and it is removed. By a new harrier process: it
  replaces the file carrying its own pid.
- **Host process crashes holding a lease.** The container refuses opens until
  the next host invocation clears it. `harrier doctor` exits 1 and names it.
- **A second run.** Leases are per pid. Running the same command twice
  behaves as it does today under one kernel.

Failure modes this must not introduce:

- An argument value in a lease file, a 503 body, `/health`, or `harrier
  doctor` output.
- A refusal that leaves a lease behind.
- `/health` answering non-200 because of a lease.

## What the implementation decided

Recorded here so the spec and the code agree.

- **The lease files are handled by `services/api/src/harrier/hostlease.py`;**
  `db.py` holds the decision (take, ask, give back) and the container-side
  refusal, as Scope says. A lease is written to a temporary file and then
  hard-linked to its name: `link` fails when the name exists, which makes the
  create exclusive, and a reader never sees half a lease.
- **The CLI takes the lease when it decides, not at the first open.** The
  first question only probes (`probe_database_ownership`, no lease). The
  second takes the lease and asks again (`check_database_ownership`). A
  container that started between them is seen, the lease is given back, and
  the command is handed over. This is the spec's "first open takes a lease"
  moved to the one place every CLI run passes, before logging setup and
  before the command's own opens. Host code that is not the CLI takes its
  lease at its first open, in `connect`.
- **Once a process holds a lease it owns the database** until it ends, and
  later opens in it skip the engine: the container is the side refused.
- **The 503 is declared by a route class,** `DatabaseRoute` in
  `services/api/src/harrier_api/deps.py`, which finds the `Conn` dependency
  and adds the response itself, rather than by merging a dictionary into each
  decorator. A new route that opens the database cannot forget it, and one
  that does not never claims it. FastAPI 0.141 keeps an included router whole
  rather than copying its routes, so the test walks `original_router`.
- **`/health` takes no `Conn`.** It reads the lease directory first and opens
  the database only when there is no hold. Its own process's lease is not a
  hold, so a host dev server does not report itself.
- **A lease file that cannot be read is a hold** in the container (it may be
  one being written) and is left in place by the host's dead-lease cleanup
  (it may belong to something else). `harrier doctor` does not list it.
- **The process role** is "container" when `/.dockerenv` exists
  (`harrier.container.running_in`), which Docker creates in every container.
- **Start times come from `ps -o lstart=`** in UTC, at one-second resolution.
  That resolution is the tolerance the spec asked to record: a pid reused
  within the same second its predecessor started would match.
- **Plain `harrier doctor` probes and takes no lease;** it opens nothing.
  `doctor --integrity` is a `database` command and the CLI takes its lease.
  The lease lines come before the verdict, so the verdict stays last.
- **Specs 061 and 074's tests changed with the behaviour.** Their fixtures now
  default to "no engine", play the host, and give back any lease a test took,
  because a process holding a lease is no longer refused. Spec 061's CLI
  refusal test uses the host-path refusal, which is the one a container-owned
  database still produces from the CLI.

## Limitations found at implementation

- **A lease lasts as long as its process.** A host command that opened the
  database once, for logging setup, holds its lease until it ends, and a
  container that starts meanwhile answers 503 until then. Releasing earlier
  would be safe only once every connection is known to be closed, which is
  spec 076's subject.
- **The lease directory stays once created.** A host command run while the
  container owns the database takes a lease, learns it is refused, and gives
  it back, leaving `data/host-db-owners/` empty. An empty directory holds
  nothing out.

## Data and privacy

The lease, the 503 body, `/health` and `harrier doctor` carry the subcommand
name only, proven by the sentinel criterion. Lease files are never-in-git
under `data/**`.

## Honest limitations

- **The lease depends on file creation being visible across the mount
  promptly.** Exclusive create is resolved by the host filesystem, but how
  quickly the VM sees a new file under `data/host-db-owners/` was not
  measured. A directory listing cached in the VM would reopen the race for
  that long. This is the least certain mechanism of the three specs.
- **Start time comparison needs a tolerance.** How a process start time is
  read on macOS, and how exact it is, is recorded by amendment. Too loose a
  tolerance weakens the pid reuse check.
- **A long host run blocks the web app.** Pages that read the tracker show the
  503 body through their existing error text, which is plain and not
  designed.
- **The cross-kernel behaviour is not pinned by CI.**

2. `harrier doctor` should exit 0.
